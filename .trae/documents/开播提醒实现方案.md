# 主播开播提醒 — 实现方案（已落地版）

## Context

需求已锁定：**关注若干抖音主播，有人开播就推消息到个人微信，网页关掉也生效**（个人自用，不做登录注册，只做抖音，不做历史记录）。

推送走本机已运行的 nanobot 网关（`python -m nanobot trigger <ID> "消息"` → 微信）。但巡检脚本要"知道该监控谁"，就必须让关注列表离开浏览器本地存储、落到**网页与脚本都能读到**的地方。

### 执行期的关键转向：存储从云 PG 改为本地文件

原方案（见文末"方案演进"）打算把关注列表存进 CloudBase 的 PostgreSQL。**执行时确认这条通道不可用**，因此改成本地文件，架构反而更简单、零云依赖。

探测结论（均实测）：

1. 该环境是 PG（`RuntimeMode: "postgresql"`，只有实例 `pgdb-1j4zick3`），**没有文档库**。`readNoSqlDatabaseStructure` 直接报错：`[ListTables] This environment has no document database instance ... Use the ExecutePGSql action`。
2. 但当前 MCP **只挂了** `auth` / `queryEnv` / `manageEnv` / `envDomainManagement` / 读写 NoSQL / `manageDataModel` / `modifyDataModel` / `queryAgents`。**没有 `managePgDatabase`、没有 `ExecutePGSql`、没有云函数部署工具、没有 `callCloudApi`**（多次精确名与关键词检索均为 0 个结果）。
3. 本机也没有 `tcb` CLI，无法自行部署云函数。

结论：云 PG 这条路上"建表"和"部署云函数"两个动作都执行不了，方案不可落地。**经确认改为本地文件持久化**。

## 最终架构

```
浏览器（Taro H5, dist-h5/）
   │  POST /api/getUserFollows、/api/toggleFollow
   ▼
scripts/serve-h5.js ── 本地实现这两个"云函数"，读写 scripts/follows.json
   │  POST /api/getStreamerStatus（同源代理，规避 CORS）
   ▼
CloudBase HTTP 网关 ── 云函数 getStreamerStatus ── 抓抖音 SSR 页
                                                        │
scripts/watch-live.js ── 每 60 秒读同一个 follows.json ──┘
   │  python -m nanobot trigger <ID> "开播了…"
   ▼
个人微信
```

关键点：**`scripts/follows.json` 是关注列表的唯一真源**，网页和巡检脚本共用同一份文件，不需要任何数据库。前端 `services/cloud.ts` 完全不感知来源差异——本地接口与云函数返回同一套 `{code, message, data}` 契约。

## 实现清单

### 1. 关注列表存储（新增 `scripts/follows-store.js`）

- `FILE` = `scripts/follows.json`
- `normalizeUniqueId(input)`：支持直接填抖音号，也支持粘贴 `https://live.douyin.com/xxx`（去协议头、去 query/hash、去尾斜杠）
- `readFollows()` / `writeFollows(list)`：读失败（文件不存在/损坏）返回 `[]`，不抛错
- 写入用 `写临时文件 + renameSync`，避免半截文件把数据写坏

### 2. 本地"云函数"（改 `scripts/serve-h5.js`）

在 `/api/*` 分支最前面插入 `LOCAL_HANDLERS` 命中判断，命中则本地处理，否则转发 CloudBase 网关：

- `getUserFollows` → `{ followedIds, streamers }`（`streamers` 是给巡检脚本用的完整信息，一次调用拿全）
- `toggleFollow` → `follow` 走 upsert（存在则合并、保留 `createdAt`，不存在则追加并写入 `createdAt`）；`unfollow` 走过滤删除；参数不合法返回 `code:-1`
- 记录字段固定包含 `platform: 'douyin'`——缺了它 [StreamerCard](file:///d:/小程序/src/components/StreamerCard/index.tsx) 的 `platformMap[streamer.platform]` 会拿到 `undefined`
- 用 `Object.prototype.hasOwnProperty.call(LOCAL_HANDLERS, name)` 判断，防原型污染
- 新增 `readBody` / `sendJson` 辅助函数

### 3. 前端

**改 [cloud.ts](file:///d:/小程序/src/services/cloud.ts) — 加 `fallback` 选项**

```ts
callFunction<T>(name, data?, opts?: { fallback?: 'mock' | 'none' })
```

- 写操作（`toggleFollow`）和关注列表读取一律传 `'none'`：失败直接抛错，**绝不回退 mock 伪造成功**
- 只读展示类调用保留 `'mock'` 兜底，保证页面不白屏

**改 [streamer.ts](file:///d:/小程序/src/services/streamer.ts)**

- `getStreamerStatus` 接受 `{ streamerId?, uniqueId? }`（云函数本来就支持传 `uniqueId`，只是 service 层没暴露）
- `toggleFollow(target, action)` 入参带 profile（`uniqueId`/`name`/`avatar`/`roomUrl`），失败必须抛错
- `getUserFollows` 返回类型加 `streamers`

**改 [store/streamer.tsx](file:///d:/小程序/src/store/streamer.tsx) — 核心堵点**

- 删掉 `isWeapp` 分支与 `Taro.getStorageSync` 本地存储真源，**双端统一走接口**
- 保留乐观更新 + 失败回滚（回滚 `follows` 与 `followedIds`）+ Toast
- 抖音号格式校验 `^[\w.-]+$`，非法则提示"该主播未接入抖音号"

**改 [subscribe/index.tsx](file:///d:/小程序/src/pages/subscribe/index.tsx)**

- 顶部"开播提醒"卡片，**删掉纯本地 state 的假 Switch**，副文案改为"本机每分钟巡检一次，开播即推送微信"
- 新增"输入抖音号 → 添加"栏。流程：`getStreamerStatus({uniqueId}, {fallback:'none'})` 校验并取真实昵称/头像 → `toggleFollow(profile)` 落盘 → 更新状态 → Toast。抖音号不存在或查询失败要给出明确提示，不静默失败
- 列表数据源从静态 mock `src/data/streamers.ts` 改为 `getUserFollows()` 返回的 `streamers`，并入实时状态、按"直播中"排前
- 进页面拉一次状态，之后每 60 秒轮询

**统一按 `uniqueId` 判断关注关系**：`home` / `discover` / `search` / `mine` / `streamer-detail` 各页面的 `isFollowed` / `followedIds.includes` 全部改为传 `uniqueId`。

### 4. 巡检 + 推送（新增 `scripts/watch-live.js`）

- **直连 CloudBase HTTP 网关**，不走 `localhost:3000` 代理，这样不用先开着 `serve:h5`
- 每 60 秒一轮：读 `follows.json` → 逐个 `getStreamerStatus({uniqueId})` → 比对本地状态 → 命中开播则 `python -m nanobot trigger <ID> "<消息>"`
- **用链式 `setTimeout`，不用 `setInterval`**（一轮耗时超过 60 秒时 `setInterval` 会叠加）
- 消息内容：主播名 + 直播间标题 + 在线人数 + 直播间链接
- 用 `spawn(nanobotExe, [...args, 'trigger', id, message], { shell: false })`——**shell:false + 参数数组**，避免中文与换行被 shell 吞掉
- 状态文件 `scripts/.watch-state.json`，字段 `{ status, sessionKey, lastCheckedAt }`
- 命令行开关：`--once`、`--test-notify`、`--reset`

**状态机与去重（这里最容易写出"每分钟骚扰一次"的 bug）**

- 主判据：`offline → living` 翻转才推
- **不能用 `roomId` 当唯一键**：实测离线时也返回 roomId
- **绝不能用 `liveStartTime` 当键**：[getStreamerStatus/index.js:162](file:///d:/小程序/cloudfunctions/getStreamerStatus/index.js#L162) 在 `create_time` 缺失时会退化成 `Date.now()`，每次调用都变，会导致每分钟判成"新场次"→ 每分钟推一次
- 识别新场次只能靠：状态从 offline 翻转，或持续 living 且 `|startTime - sessionKey| > 5min`
- 返回 `code: -1`（抖音风控/超时）→ **不翻转状态、不推送**，保留上次已知状态
- 状态文件丢失 / 首次启动 → 以当前状态**静默 seed**，不补推历史

### 5. 工程杂项

- **`config/index.ts` 输出目录分流**：`outputRoot: process.env.TARO_ENV === 'h5' ? 'dist-h5' : 'dist'`。原来 build:h5 写到 `dist/`，而 `serve-h5.js` 读 `dist-h5/`，导致浏览器一直在看旧产物
- **新增根目录 `.gitignore`**（项目此前没有）：忽略 `node_modules/`、`dist/`、`dist-h5/`、`.swc/`、`.pai/`、`scripts/follows.json(.tmp)`、`scripts/.watch-state.json(.tmp)`、`scripts/watch-live.config.json`（含 trigger ID）
- **`package.json`** 加 `"watch:live": "node scripts/watch-live.js"`
- **`scripts/watch-live.config.json`**（已 gitignore）：`triggerId` / `nanobotExe` / `nanobotArgs` / `gatewayHost` / `intervalMs`

> 注意：`nanobotExe` 必须写**真实解释器绝对路径**（`C:\Users\23374\AppData\Local\Programs\Python\Python314\python.exe`）。PATH 里的 `python.exe` 是 Windows 商店占位程序，会以退出码 9009 失败。

**当初为什么发现页是假的**：抖音没有公开的"主播目录/榜单"接口，SSR 方案只能按 `uniqueId` 逐个查——必须先知道"是谁"，才能查"在不在播"。而发现页的需求本质是"列出我不知道的主播"，从头就没有真实数据源，当初是用 mock 把 UI 撑起来的。

`cloudfunctions/getStreamerList` 也已失效：它在 PG 环境下查 `db.collection('streamers')` 必然抛错，被 `try/catch` 静默吞掉后返回硬编码的 5 条（其中 4 条连 `uniqueId` 都没有、头像用 `picsum.photos` 随机占位图、PDD/冯提莫还标成 bilibili），随后试图写回数据库同样静默失败。前端调用入口已删除，云函数本身保留未动。

**教训**：早期验收把首页/发现笼统归到"验证通过"，没有区分真实链路与假数据——这是本次信任受损的直接原因。以后验收必须逐页说明数据来源。

## 已知限制（不在本次范围）

- **电脑关机时收不到提醒**（巡检脚本跑在本机）
- 巡检脚本由你手动开终端运行，重启电脑后需重新启动（你已确认接受）
- **网页服务同样不自启**：`scripts/serve-h5.js` 是手动起的进程，电脑重启（或终端被关掉）后网页打不开，浏览器显示"服务不可用"。重启电脑后需手动 `npm run serve:h5`。
  注意**"网页查询"和"微信推送"是两件独立的事**：只跑 `watch:live` 不跑 `serve:h5`，提醒照常推，只是网页打不开——排查时容易把两者混为一谈
- 每个主播每轮巡检产生 2 次抖音请求（取 cookie + 房间页），主播增多后需改批量接口

### 若将来要做到"电脑关机也能收到"

两条路，都不需要改前端（关注列表契约不变）：

1. **搬到常开设备**：把 `watch-live.js` + nanobot 放到一台常开的机器或云主机（crontab / 计划任务跑 `--once` 即可）。改动量最小，本机脚本原样可用。
2. **全云端**：用云函数定时触发器替代本机脚本，推送改走微信服务号/企业微信机器人 webhook。**前提是先解决本次的两个工具阻断**——需要能部署云函数的通道（`tcb` CLI 或 GitHub Action），以及一个可用的推送出口（PushPlus / 企业微信机器人 webhook 均可，不需要 nanobot）。关注列表可继续用 HTTP 数据接口，或届时再谈迁 PG。

## 方案演进（存档）

初版方案假定关注列表存 CloudBase PG，分四阶段：阶段 0 云函数内 `app.rdb()` 探针 + 建 `follows` 表；阶段 1 改造 4 个云函数走 PG；阶段 2 前端加 `fallback` 选项并统一双端走云函数；阶段 3 本地巡检脚本。

**阶段 0 在执行时被判定为不可落地**（无 PG 工具、无部署工具、无 `tcb` CLI），经确认整体改为本地文件方案。阶段 2、阶段 3 的设计（`fallback` 选项、巡检状态机与去重规则）**原样保留并已实现**——这部分设计与存储介质无关。
