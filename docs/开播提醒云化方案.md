# 开播提醒云化方案

> 生成时间：2026-10-31
> 背景原方案：本机常驻 `scripts/watch-live.js`（秒级评估 + nanobot 推送），电脑关机即失效
> 本方案把巡检与推送搬进微信云开发，实现「关机也提醒」，本机脚本降级为备用

---

## 一、现状对照

| | 本机方案（原） | 云函数方案（本） |
|---|---|---|
| 巡检驱动 | 本机 Node 进程 + 链式 setTimeout | 云开发定时触发器（每分钟） |
| 常驻要求 | 电脑必须开机 | 无（云端执行） |
| 状态存储 | `scripts/.watch-state.json` | 云数据库 `watchState` 集合 |
| 推送通道 | nanobot trigger → 微信 | 云调用 `subscribeMessage.send`（订阅消息） |
| 额度模型 | 无限制 | 一次性订阅：用户点一次「允许」攒一条 |
| 故障感知 | 静默（沿用旧状态） | 连续失败 ≥3 轮发故障告警 |
| 失效场景 | 关机/进程被杀 | 抖音改版（同源风险）+ 用户没攒额度 |

判定逻辑两者共用 `cloudfunctions/_shared/watch-rules.js`（首见静默 / offline→living 推 / 开播时间跳变 >5min 换场推）。

## 二、链路图

```
定时触发器（每分钟）
   │
   ▼
cloudfunctions/watchLive
   ├─ 1 读取 follows 集合（跨用户；管理端 SDK）
   ├─ 2 按 uniqueId 去重，云函数间调用 getStreamerStatus（复用其 SSR 解析 + 25s 缓存）
   ├─ 3 逐用户（openid）评估 watch-rules → watchState 落库
   └─ 4 翻转命中 → subscribeMessage.send（每个订阅者消费一条额度）
失败分支：连续 ≥3 轮 → fail__ 计数 → 冷却窗口内推故障告警
备用链路：本机 watch-live.js（同一判定规则；与云端不要同时开推，避免同一场双推）
```

## 三、watchLive 云函数

```
cloudfunctions/watchLive/
├─ index.js            主流程（读库 → 查询 → 判定 → 推送 → 失败计数）
├─ package.json        wx-server-sdk ~2.6.3
├─ config.json         权限 + timeout 60s + 定时触发器 "0 */1 * * * * *"
└─ watch-config.json   推送配置（模板 ID / 字段映射 / 跳转路径）
```

### watch-config.json 字段说明

| 字段 | 含义 |
|---|---|
| `templateId` | 开播通知模板 ID（订阅消息 → 公共模板库获取；空=只巡检不推送） |
| `alertTemplateId` | 故障告警模板 ID（可与 templateId 共用同一个） |
| `page` | 点击消息跳转页；`{uniqueId}` 占位符会被替换成抖音号 |
| `miniprogramState` | `formal` 正式版 / `trial` 体验版 / `developer` 开发版。用体验版调推送时改 `trial` |
| `keys` | 业务字段 → 模板字段的映射（notify-data.js 的取值器见下） |
| `alertKeys` | 故障告警的字段映射 |

可进 data 的业务字段（`_shared/notify-data.js`）：`name`、`roomTitle`、`viewerCount`、`liveStartTime`；告警侧：`detail`、`failedAt`。字段必须有值才写入 data（模板必填字段留空会 send 失败，宁可少一两个字段）。单字段超长截断到 32 字符。

`scripts/notify-data.test.js` 会校验 watch-config.json 的映射键名确实配得上取值器——字段名写错会在单测立刻暴露，而不是上线后静默丢字段。

## 四、数据模型（watchState 集合）

| doc `_id` | 内容 | 用途 |
|---|---|---|
| `${openid}__${uniqueId}` | `{ openid, uniqueId, status, sessionKey, lastCheckedAt }` | watch-rules 逐用户判定的输入输出 |
| `fail__${uniqueId}` | `{ failCount, lastError, failedAt, lastAlertAt }` | 连续失败计数与告警冷却 |

- 集合权限设「仅创建者可读写」即可：业务代码全部走管理端 SDK（云函数），不受集合权限影响；前端不直接读该集合。
- 查询成功清除对应 `fail__` 计数；`failCount === 3` 或超过冷却（1h）再次触发告警。

## 五、额度模型与交互（一次性订阅的约束）

个人主体小程序只有**一次性订阅消息**：

1. 用户在小程序里点「开启」→ 弹系统授权 → 同意后为该模板攒 **1 条** 推送额度
2. 主播开播时，watchLive 消费 1 条额度发通知；没额度（errCode 43101）不打扰、不算异常
3. 每次打开小程序都可再点「开启」补额度（入口在订阅页的通知栏右侧）
4. 部分机型勾选「总是保持以上选择，不再询问」后，额度自动续——体验更顺滑

这是产品行为的一部分：**没有攒过额度的用户不会收到推送**。README 已如实标注。

## 六、已知限制与取舍

1. **同一用户两链路不能同时开**：云端与本机脚本的状态文件互不同步，同一场直播可能收到两次通知。切到云端运行后，本机 `watch-live.js` 建议只作开发调试用（或 `--reset` 后停止）。
2. **watchState 不会自动萎缩**：用户取关后对应 `${openid}__${uniqueId}` 文档留存（evaluate 会覆盖写但不会删）。个人量级可接受；若做多用户开放，需要加清理任务（对比 follows 全集分页删除孤儿状态）。
3. **抖音改版风险同源**：watchLive 与 getStreamerStatus 共用解析路径，改版即全链路失效——这正是故障告警存在的原因（连续 3 轮失败主动推告警）。
4. **定时触发有 ± 漂移**：云开发分钟级触发器非精确时刻，正常误差秒级，不影响「开播即推」的体验目标。
5. **page 字段约束**：正式版推送 page 必须存在于已发布版本；体验/开发版推送需把 `miniprogramState` 改为对应值。

## 七、部署与验证

操作步骤（含注册、环境创建、模板申请）见《小程序注册与云开发迁移指引.md》。

部署后的端到端验证清单：

- [ ] 云开发控制台 → watchLive → 云端测试（无参调用）→ 返回 `{ code: 0 }`，日志出现「本轮完成」
- [ ] 空跑日志：follows 有记录时逐主播 `查询成功`；watchState 出现 `${openid}__${uid}` 文档
- [ ] 关注一个**正在直播**的抖音号 → 下一两分钟收到订阅消息，点开落到详情页
- [ ] 故意把 getStreamerStatus 里 UA 改坏制造连续失败 → 第 3 轮收到故障告警 → 改回后计数归零
- [ ] 关机测试：电脑关机状态下开播的主播，微信仍收到提醒（本方案的验收标准）
