# 扩展接缝设计（自用 → 开源/多用户）

> 状态：**设计文档**。当前代码按「自用」运行，本文档定义未来扩展的接缝，
> 以及为了保住这些接缝，现在**必须遵守的约束**。

## 一、目标

现在：单人使用，H5 用本地文件，小程序用云数据库。

未来可能：开源后他人部署，或多用户使用。

**不现在做多用户**，但要保证未来切换的成本是「换一个适配器」，而不是「重写业务逻辑」。

## 二、三条必须预留的接缝

### 接缝 1：数据访问接口（最重要）

**问题**：现在 `src/services/streamer.ts` 直接调用 `callFunction('getUserFollows')`，
函数名、入参、返回结构都是隐式约定，散落在前后端两侧。

**现状的耦合点**：

```
前端                          后端
services/streamer.ts   ←→    cloudfunctions/getUserFollows
  callFunction(name, data)      exports.main(event)
```

契约靠「两边都记得改」维持。改一个字段名要同时改 4 处（前端 service、
H5 本地 handler、云函数、以及 watch-live 脚本）。

**接缝设计**：

```ts
// src/services/ports.ts —— 只定义契约，不含实现

/** 关注数据仓储 */
export interface FollowRepository {
  list(): Promise<{ followedIds: string[]; streamers: FollowedStreamer[] }>;
  follow(target: FollowTarget): Promise<{ followed: boolean }>;
  unfollow(uniqueId: string): Promise<{ followed: boolean }>;
}

/** 直播状态查询 */
export interface LiveStatusProvider {
  query(uniqueId: string): Promise<LiveStatusResult>;
}
```

实现可以有多个：

| 实现 | 用在哪 |
|---|---|
| `CloudFollowRepository` | 现在（H5 走 /api，小程序走 Taro.cloud） |
| `LocalFollowRepository` | 未来：纯前端 localStorage（离线优先） |
| `RestFollowRepository` | 未来：开源后他人接自己的后端 |

**关键约束**：业务代码（store / hooks / pages）**只依赖接口，不依赖具体实现**。

### 接缝 2：身份来源

**问题**：现在 `_openid` 由微信注入，H5 没有身份概念。

**接缝设计**：

```ts
/** 当前用户标识 */
export interface IdentityProvider {
  /** 返回稳定的用户标识；匿名场景返回设备级 ID */
  currentUserId(): Promise<string>;
}
```

| 实现 | 场景 |
|---|---|
| `WeappIdentity` | 小程序：用 `_openid`（服务端注入，前端拿不到也不该拿） |
| `AnonymousIdentity` | H5 自用：返回固定值 `'local'` |
| `DeviceIdentity` | 开源后：localStorage 里持久化的 UUID |

**关键约束**：数据层**不假设**一定有 `_openid`。查询条件里的用户维度
要通过接口拿，不能硬编码 `where({ _openid })`。

> 这条现在做不到（云函数里写死了 `_openid`），但**文档化这个约束**，
> 未来改的时候知道要动哪里。

### 接缝 3：存储实现

**问题**：`follows-store.js` 是文件，云函数是数据库，两套代码。

**接缝设计**：

```js
// 仓储接口（Node 侧）
interface FollowStore {
  readAll(): FollowedStreamer[]        // 或 Promise
  writeAll(list: FollowedStreamer[]): void
}
```

| 实现 | 场景 |
|---|---|
| `JsonFileStore` | 现在（scripts/follows-store.js） |
| `CloudDbStore` | 未来（云数据库） |
| `SqliteStore` | 未来（本地单机但需要查询能力） |

**关键约束**：`serve-h5.js` 只依赖 `FollowStore` 接口，不直接 `require('follows-store')`。

## 三、现在就要做的最小改动

不需要引入依赖注入框架。三件小事就能保住接缝：

### 1. 把契约写成类型文件

`src/services/ports.ts` —— 只有 interface，没有实现。约 40 行。

收益：任何人（包括未来的你）看这一个文件就知道数据层要提供什么。

### 2. 让 service 返回「领域对象」而不是「云函数原始返回」

现在：

```ts
return callFunction('getUserFollows', {})  // 直接透传后端结构
```

改为：

```ts
const raw = await callFunction('getUserFollows', {})
return toFollowList(raw)   // 归一化，后端换结构只改这一处
```

收益：后端换实现时，只有归一化函数要改。

### 3. 把函数名收进常量

现在 `callFunction('getUserFollows')` 里字符串散落各处。

```ts
export const RPC = {
  getUserFollows: 'getUserFollows',
  toggleFollow: 'toggleFollow',
  getStreamerStatus: 'getStreamerStatus'
} as const
```

收益：改函数名只改一处；也方便未来映射到 REST 路径。

## 四、明确**不做**的事

| 不做 | 原因 |
|---|---|
| 引入 DI 容器 | 单人项目，过度设计 |
| 现在就写多后端实现 | 没有第二个使用场景，写了也是死代码 |
| 现在做用户系统 | 明确不需要 |
| 把 `_openid` 抽象掉 | 小程序端它就是唯一正确解，抽象反而绕 |

## 五、开源前必须补的清单

如果未来要开源，除了上面的接缝，还需要：

1. **真实 AppID 不能进仓库** —— 现在 `project.config.json` 是 `touristappid`，开源前要确认没有真实 ID
2. **云环境 ID 要可配置** —— 已支持 `TCB_ENV_ID` 环境变量 ✅
3. **`scripts/follows.json` 等个人数据要 gitignore** —— 已做 ✅
4. **README 要写清部署前提** —— 云开发环境、集合创建、权限配置
5. **LICENSE 文件** —— 开源协议
6. **`.env.example`** —— 列出所有环境变量
7. **CI** —— 至少跑 `typecheck` + `test` + `check:rules`

## 六、判断标准

> **接缝做对了的标志**：未来想加一个「SQLite 本地存储」实现，
> 不需要改任何 page / hook / store 代码，只新增一个实现文件 + 改一处工厂。

如果做不到这一点，说明接缝没做对。
